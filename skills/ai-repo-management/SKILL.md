# AI Repository Management

Manage the AI toolkit at `~/AI/` — skill placement, collection syncing, plugin
distribution, and manifest integrity.

## How it fits together

The `~/AI/` repo is the **framework**: it owns the distribution machinery
(`scripts/sync.sh`, the `local.yaml` collection contract, the
`external-skills.yaml` manifest, and the `.claude-plugin/marketplace.json`).
**`ai-private`** is a separate private content repo that **hooks into** the
framework declaratively — it registers itself as a collection and is published
as a plugin; it adds no machinery of its own. Content reaches clients through
two paths: **toolkit sync** (collections → `sync.sh` → `~/AI/*` symlinks, read
by all clients) and the **Claude Code plugin** (marketplace → `/plugin install`).

## Read these first (source of truth)

> The repo layout, where each skill lives, and the distribution paths **shift
> over time**. Do not trust any structure reproduced from memory — Read the
> current state from these files before acting:

| For… | Read |
|------|------|
| Framework mechanism (collections schema, `links:` rules, repo model) | `~/AI/README.md`, `~/AI/docs/collections.md`, `~/AI/docs/skills-agents-architecture.md` |
| **Live registry** — what is actually registered right now | `~/AI/local.yaml` (private/work/standalone collections), `~/AI/external-skills.yaml` (internal + git skills) |
| Collection config template / schema reference | `~/AI/local.yaml.example` |
| How `ai-private` hooks in + the two distribution paths | `~/Repositories/ai-private/README.md` |
| Plugin specifics (groups, hooks, `userConfig`) | `~/Repositories/ai-private/docs/PLUGIN.md` |

`~/AI/skills/` and `~/AI/agents/` are **gitignored** and fully generated by
`sync.sh`. Never create skills directly there — edit the source repo and re-sync.

## Responsibility Boundary

This skill owns source placement, registration, synchronization, and local
client discovery. It does not own how a source repository publishes plugins,
marketplaces, organization bundles, or standalone packages.

Treat these as separate operations:

- **Local discovery**: register sources and run `sync.sh`.
- **Repository publication**: follow the source repository's instructions and
  load its publishing skill when one exists.
- **Standalone export**: create package files only when explicitly requested.

## Creating a New Skill

### Step 1 — Choose the source repo

| If the skill is… | Put it in… | Register via… |
|------------------|-----------|---------------|
| Personal / cross-project | `ai-private/skills/<name>/` | `local.yaml` → `collections.private.skills` |
| Company / work-specific | the work skills repo | `local.yaml` → `collections.work.skills` |
| Framework itself (repo mgmt, syncing) | `~/AI/skills/<name>/` directly | `external-skills.yaml` as `type: internal` |
| From a remote git repo | the remote repo | `external-skills.yaml` as `type: git` |

### Step 2 — Create the files

```
<repo>/skills/<name>/
  SKILL.md              # Required — frontmatter (name, description) + content
  supporting-file.*     # Only if needed (heavy reference, scripts)
```

### Step 3 — Register it

Add an entry to the appropriate manifest, then **confirm the exact schema
against the live files** (`local.yaml.example`, or existing entries in
`local.yaml` / `external-skills.yaml`) rather than from memory — the keys and
options evolve. The shapes are roughly:

- **Private / work skill** → a list item under `collections.<name>.skills`
  (a bare string, or `{source, name}` when the symlink name differs).
- **Non-skill content** (config dirs, hooks) → `collections.<name>.links`
  (link **directories**, not individual written-to files — atomic-write-rename
  breaks file symlinks).
- **Internal skill** → `skills:` entry with `type: internal` in `external-skills.yaml`.
- **Git-fetched skill** → `skills:` entry with `type: git` + `source`/`branch`/`path`/`target`.

### Step 4 — Sync

```bash
cd ~/AI && ./scripts/sync.sh
```

This materializes the symlinks under `~/AI/skills/<name>` (and `~/AI/agents`,
`~/AI/hooks`, plus any `links:` targets).

## Component Types

| Type   | When to Create                                    |
|--------|---------------------------------------------------|
| Skill  | Has procedures, substantial knowledge (>10 lines) |
| Rule   | Simple constraint, <10 lines, no procedures       |
| Agent  | Composing skills for specific context              |
| Hook   | Deterministic automation on a Claude Code event   |

## Hooks (Claude Code only)

**Hooks ship as a plugin, not through `sync.sh`.** The file a human edits is not
the file that runs.

| Path | Role |
|------|------|
| `ai-private/hooks/hooks.json` | What a human edits. **Not executed.** |
| `~/.claude/plugins/cache/bobthearsonist/ai-private/<version>/hooks/hooks.json` | What Claude Code executes — a clone of the GitHub remote, pinned to a commit by `installed_plugins.json` |
| `~/AI/hooks/` | sync.sh symlinks. **Nothing reads them.** |

Delivery path for a hook change: edit → commit → **push to GitHub** → bump
`version` in `ai-private/.claude-plugin/plugin.json` (convention: a commit titled
`chore(release): bump ai-private to X.Y.Z`) → `claude plugin update
ai-private@bobthearsonist` → restart Claude Code.

**The version bump is not optional.** `claude plugin update` is version-gated,
not commit-gated: with an unchanged version it reports "already at the latest
version" and does nothing, however many commits landed. Measured 2026-09-02 —
the plugin sat pinned for ~3 months behind 22 commits, six of them changing hook
behaviour; a Grep-nudge hook was dormant the whole time with no error anywhere.

**`~/AI/hooks/` is orphaned.** `sync.sh` reads `.collections.<name>.hooks` from
`local.yaml` and symlinks those entries in (currently `run-regenerate-visual.sh`,
`run-hook.sh`, `post-obsidian-append.md`, `skill-check.sh`,
`session-start-context.md`). No Claude Code settings scope references that
directory, and the plugin resolves `${CLAUDE_PLUGIN_ROOT}` to its own cache copy
instead. Open question: whether the `hooks:` key in `local.yaml` should be
dropped.

**Other clients get no hooks.** `docs/client-support.md` names four shared
surfaces — Instructions, Skills, Agents, Permissions — and hooks are not among
them. opencode's config has no `hooks` key; Copilot CLI sets
`"disableAllHooks": true`. Git hooks (via `core.hooksPath`) are the only
genuinely cross-client hook mechanism, because they hang off git rather than off
a client.

## Troubleshooting

**Skill not loading?**
1. Check the symlink exists: `ls -la ~/AI/skills/<name>`
2. If missing, confirm it's listed in `local.yaml` or `external-skills.yaml`
3. Run `./scripts/sync.sh` and check for errors
4. Verify the source directory exists at the configured `path`

**Plugin component not appearing?** See `ai-private/docs/PLUGIN.md` — likely the
plugin isn't enabled in `~/.claude/settings.json`, or Claude Code needs a restart.

**Sync failing?**
- `yq` must be installed (sync.sh parses YAML with it)
- On Windows: `MSYS=winsymlinks:nativestrict` is set automatically
- Git-fetched skills need network access on first clone

## Quick Validation

```bash
cd ~/AI

# Sync everything
./scripts/sync.sh

# Find broken symlinks
find skills/ -maxdepth 1 -type l ! -exec test -e {} \; -print

# List what is registered right now (the live source of truth)
echo "=== external-skills.yaml ===" && yq '.skills[].name' external-skills.yaml
echo "=== local.yaml collections ===" && yq '.collections[].skills[]' local.yaml
```
