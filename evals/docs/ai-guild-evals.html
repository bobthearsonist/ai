What we evaluate

Triggering

Does the skill activate when appropriate, including implicit requests? Does it stay out of unrelated negative-control tasks?

Behavior

Explicit checks inspect answer text, tool order or supported file outcomes. A passing sample satisfies those checks, not every aspect of quality.

Added value

Repeated with/without arms compare outcomes on the same case definitions. A smoke verifies the path, not the benefit of the skill.

The model output is variable; grading is deterministic. The same captured transcript receives the same supported check results under the same policy. A separately approved AI judge can archive advisory assessments, but never changes these deterministic scores. Nine positive cases now have per-case semantic rubrics that accept equivalent reasoning instead of relying on keywords or short proximity windows. These rubrics have not been calibrated with live judge runs; syntax, activation and disclosure checks stay deterministic. See the semantic judge adoption notes.

Quick start: offline validation and planning

Use Node.js 22.12+ with matching ai and ai-evals sibling checkouts. These commands do not launch a model.

Set-Location C:\Repositories\ai\evals
npm ci --ignore-scripts
npm test
node local\cli.mjs validate --suite git-commit-style
node local\cli.mjs run --suite git-commit-style --dry-run
node local\cli.mjs run-all --dry-run

Native ACP acceptance still needs a separately approved live run. Preflight verifies local runtime/policy and credential readiness, not provider access. Do not provide API-key overrides, copy credentials or treat a custom ACP profile as proof of native isolation.

This suite has three cases: 3 cases x 3 repeats x 2 arms = 18 live sessions for one runner. Each additional runner increases that count. Use the development engine's run-all --dry-run to inspect the planned count before running all suites. Do not copy an approval count blindly.

Read the result, not just the green number

Consumer artifacts stay under evals\.work\local-runs. Open the run's normalized.json for client/version, status, case scores, cost and caveats. Archived traces live under traces\<case>\<arm>-<n>.jsonl. The development orchestrator writes smoke-summary.md separately from full-run summary.md. Full runs also maintain result history.

With/without scores summarize passed checks. Lift means all observed with-skill scores exceeded all without-skill scores; regression is the reverse. Overlap is inconclusive; an absolute mean delta below 0.05 is reported as same. A missing arm is unmeasured. These are descriptive labels, not statistical significance tests.

Regrade an archived run without another model call:

node C:\Repositories\ai-evals\local\cli.mjs regrade C:\Repositories\ai\evals\.work\local-runs\RUN_DIRECTORY --config C:\Repositories\ai\evals\evals.json --suite git-commit-style

Recorded-policy replay preserves the run's original checks; applying the current suite requires explicit policy selection and a separate assessment. V2 file-existence checks are refused without filesystem snapshots; legacy v1 replay retains its historical skip behavior. Never compare scores across different case definitions, client versions or models as if those were controlled experiments.

Add a case where the cases belong

  1. In the consuming repo, add a Gherkin scenario in a .feature file under evals\local\cases\SKILL, not inside the distributed skill. Keep skill source unchanged during a comparison.
  2. Use a unique @case:id tag, a trigger-expectation tag, a prompt Doc String and the engine's controlled assertion vocabulary. Keep passing and failing samples in a companion id.samples.json; they are never sent to the model.
  3. Include explicit-positive, implicit-positive and negative-control coverage. Put required synthetic inputs in the suite's fixtures directory.
  4. Check evals.json for suite mapping and skill roots. Validate and dry-run with the development checkout. Run consumer tests against a compatible development engine before considering a live run.

Do not encode the answer key in the skill or fixture the model receives. See the engine README for the full schema and runner-specific restrictions; v2 file checks are unavailable without captured filesystem snapshots.

Boundaries before sharing or scaling

Current ACP runs are labelled acp-non-hermetic; historical native runs retain native-authenticated-non-hermetic and are no longer supported for replay. Fresh configuration and tool restrictions are not an OS sandbox or independent credential boundary. Subscription usage still consumes account allowance. The ACP runner does not enforce a hard spend cap; unknown USD cost remains unknown.

Review transcripts before sharing: prompts, answers, paths and tool output may contain source code or sensitive information. Keep raw artifacts local and out of Teams and Git by default. CI rollout, publication and remote dependency-pin updates are separate, explicitly approved steps.
